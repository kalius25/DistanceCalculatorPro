Backlog – Logging & Observability

Mục đích: Các hạng mục dưới đây không nằm trong Roadmap hiện tại. Chỉ xem xét triển khai khi ứng dụng phát triển thành hệ thống lớn hơn (Web API, Server, Cloud hoặc Microservices).

BL-LOG-01 – Correlation ID
Mục tiêu

Sinh một ID duy nhất cho mỗi lần thực hiện Calculate.

Ví dụ

Correlation ID
4c9c0f1d0e5d4d2d

Mọi log của lần tính toán đó đều mang cùng Correlation ID.

Ví dụ

CALCULATION_STARTED
CALCULATION_COMPLETED
ENGINE_STARTED
ENGINE_COMPLETED

đều có

correlation_id=4c9c0f1d0e5d4d2d
Lợi ích
Tra cứu nhanh toàn bộ quá trình xử lý.
Thuận tiện khi phân tích lỗi.
Chuẩn bị cho hệ thống phân tán sau này.
Khi nào cần
Web API
Server nhiều request đồng thời
Cloud
Multi-thread

Ưu tiên hiện tại: Thấp

BL-LOG-02 – Request Context
Mục tiêu

Tự động gắn metadata chung vào mọi log.

Ví dụ

Provider
TravelMode
RoutePreference
RetryCount
ApplicationVersion

Không cần truyền đi truyền lại ở từng LoggingEvent.

Lợi ích
Log đồng nhất.
Dễ phân tích.
Ít code lặp.
Khi nào cần

Khi metadata ngày càng nhiều.

Ưu tiên hiện tại: Thấp

Khi bắt đầu tối ưu tốc độ.

BL-LOG-11 – Logging Coding Standard
Mục tiêu

Thiết lập quy chuẩn cho toàn bộ dự án.

Ví dụ

Business không gọi logger trực tiếp.
Chỉ LoggingEvents được ghi log.
Không log dữ liệu nhạy cảm.
Không log HTML hoặc object lớn.
Không log trùng exception.
Không log request đầy đủ.
Event phải có tên chuẩn.
Lợi ích

Giữ kiến trúc logging thống nhất khi dự án mở rộng.

Khi nào cần

Khi nhóm phát triển có nhiều lập trình viên hoặc dự án tiếp tục phát triển.

Ưu tiên hiện tại: Thấp

Theo tôi, đây là thời điểm phù hợp để đóng EX-006. Hệ thống logging đã đáp ứng tốt nhu cầu của ứng dụng desktop hiện tại: có quản lý tập trung, sự kiện chuẩn hóa, xử lý exception đúng cách, log có cấu trúc và bảo vệ dữ liệu nhạy cảm. Các hạng mục còn lại đều là các năng lực mở rộng, nên để trong backlog sẽ giúp roadmap chính tập trung hơn mà vẫn có định hướng rõ ràng nếu dự án phát triển trong tương lai.
