ADR-031 — Logging Architecture

Status: Approved

Date: 2026-07-22

Supersedes: None

Context

DistanceCalculatorPro đã hoàn thành Exception Architecture (ADR-027 ~ ADR-030).

Hệ thống đã có:

Exception Hierarchy
ErrorCode Registry
Business Service
Provider Layer
Engine Layer
Parser Layer

Tuy nhiên chưa có kiến trúc Logging thống nhất.

Nếu mỗi module tự cấu hình logging sẽ dẫn đến:

cấu hình trùng lặp
log không nhất quán
khó chuyển sang Production Logging
khó tích hợp ELK/Loki/Cloud Logging
Decision

DistanceCalculatorPro sử dụng Centralized Structured Logging Architecture.

Toàn bộ cấu hình logging nằm trong package:

app/logging/

Business Layer không được phép tự cấu hình logging.

Architecture Principles
LA-001 Centralized Logging

Logger được khởi tạo duy nhất bởi

LoggingManager

Không module nào được gọi:

logging.basicConfig(...)

hoặc tự tạo handler.

LA-002 Layer Responsibility

Mỗi layer chỉ log đúng trách nhiệm của mình.

Layer	Logging Responsibility
Controller	Request lifecycle
CalculationService	Business flow
Provider	Provider selection
Engine	Browser automation
Parser	Parsing
Models	No logging
LA-003 Log Exception Once

Một Exception chỉ được ghi log đúng một lần.

Exception được log tại

CalculationService

Các layer khác chỉ:

raise

không được

logger.exception(...)
LA-004 Structured Logging

Logging sử dụng structured message.

Ví dụ

event=ENGINE_ERROR
provider=GoogleWebProvider
engine=GoogleMapsEngine
origin=...
destination=...
error_code=ENGINE_ERROR
LA-005 Models Are Pure

Các Domain Model không được import logging.

LA-006 Logging Configuration Isolation

Business Layer không biết:

formatter
handler
file
console
JSON

Mọi cấu hình nằm trong

app/logging/
LA-007 Production Ready

Thiết kế sẵn sàng cho:

Rotating File
Daily Log
JSON Formatter
ELK
Loki
Cloud Logging

mà không cần sửa Business Layer.

LA-008 Logging Has No Side Effect

Logging không được:

swallow exception
retry
raise exception
thay đổi business data

Logging chỉ ghi nhận thông tin.

LA-009 Module Logger

Mỗi module sử dụng logger riêng.

Ví dụ

logger = LoggingManager.get_logger(__name__)
LA-010 Lazy Initialization

Logger chỉ được khởi tạo một lần.

Các lần gọi sau chỉ trả về logger đã tồn tại.

Public API
from app.logging import LoggingManager

logger = LoggingManager.get_logger(__name__)
Directory
app/
└── logging/
    ├── __init__.py
    ├── config.py
    ├── formatter.py
    └── logging_manager.py
Consequences

Ưu điểm

Centralized Logging
Production Ready
Structured Logging
Dễ mở rộng
Dễ kiểm thử
Không coupling Business Layer

LA-011 — Event-Oriented Logging

Business Layer không được trực tiếp gọi:

logger.info(...)
logger.debug(...)
logger.warning(...)
logger.error(...)

Business Layer chỉ được phát sinh Logging Event thông qua:

LogEvents

Ví dụ

LogEvents.calculation_started(...)

không phải

logger.info(...)
Motivation
Chuẩn hóa tên event.
Không hard-code log message.
Một nơi quản lý toàn bộ Logging Event.
Chuẩn bị Structured Logging.
Chuẩn bị OpenTelemetry.
Consequence

Business Layer chỉ biết:

LogEvents

không biết:

Logger
Formatter
Handler
Output
EX-006.3.1

Đây là PB khá nhỏ.

Mục tiêu:

Xây dựng Event Catalog.

Không sửa bất kỳ service nào.

Directory
app/
└── logging/
    ├── config.py
    ├── formatter.py
    ├── logging_manager.py
    ├── log_events.py      ← NEW
    └── __init__.py
Tôi muốn điều chỉnh tên

Ban đầu tôi dùng

LogEvents

Nhưng sau khi suy nghĩ thêm, tôi thấy nên đặt là

LoggingEvents

Lý do:

Project đã có

LoggingManager

Giữ cùng prefix sẽ thống nhất hơn.

Sau này package sẽ là

LoggingManager

LoggingEvents

DefaultFormatter

nhìn sẽ đồng bộ.
